Applications submit a single-recipient plain-text message through HTTP. Campaign
composition, audience imports, and segmentation are outside this release scope.

## Required scenarios

1. Run with signup enabled against a fresh database. Create an account, configure
   a local SMTP relay, create an API key, send a message, and inspect its attempt,
   timeline, analytics, and incident bundle.
2. Repeat with signup disabled. Public signup routes must be unavailable, login
   must use the configured route, and the supported operator onboarding procedure
   must be documented and tested.
3. Test missing, invalid, revoked, and role-limited credentials. Use two isolated
   workspaces and verify denial for every resource owned by the other workspace.
4. Suppress and unsubscribe a recipient before queueing and after queueing but
   before worker processing. Neither case may submit the message to SMTP.
5. Inject transient and permanent relay failures, queue failures, database write
   failures, and worker interruption. Record recovery behavior and any ambiguous
   SMTP acceptance outcome; do not promise exactly-once SMTP delivery.
6. Deliver a signed webhook twice with the same provider event ID. Replay a
   dead-letter event twice and concurrently. Preserve suppression row count and
   original timestamp, including after partial processing failures.
7. Verify invalid signatures, stale timestamps, invalid payloads, provider batches,
   temporary bounces, permanent bounces, complaints, and unsubscribe events.
8. Inspect public and authenticated pages at desktop and mobile widths. Use real
   API data rather than demo data to validate monitoring screens.

For every run, record source revision and local changes, toolchain and dependency
versions, test fixture versions, expected and observed outcomes, and blockers.
Keep credentials, customer content, host topology, and exploit details out of
public evidence. A release requires every applicable row to pass or an explicit
owner-approved exception recorded before release.

## Auth remediation checkpoint

PR #24 merged the workspace-scoped personal keys, session-authenticated operator
pages, current membership roles, and related access checks. On PR head
`7984db3`, `make test-auth` passed against separate store/HTTP PostgreSQL
fixtures and a test Redis instance, including an upgrade from the legacy key
schema. `make verify` and the vulnerability check passed with Go 1.27.2. These
checks do not constitute a production deployment or pass the overall v1.0
release gate.

Desktop browser checks used synthetic data: key names and message subjects with
HTML markup remained literal text; logs loaded using the session; incident
attempt/provider/webhook fields matched the real API; onboarding loaded; and a
workspace admin saved policy without entering an instance key. Mobile coverage,
fresh signup, delivery recovery, and several other scenarios in the matrix remain
pending.
